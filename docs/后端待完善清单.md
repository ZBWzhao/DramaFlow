## 一、安全（最高优先，尚未开始）

### S1. `POST /api/canvas/export` 可写任意路径
- 证据：`server/app.py:2427-2438`，`relative = req.path or ...`，`target = WORKSPACE / relative`，无 `..` 校验、无 containment 检查；该接口还不校验 revision。
- 影响：构造 `path="../../x.md"` 可在进程权限内任意位置写文件，内容为可控 Markdown。
- 修法：统一 `safe_workspace_path(requested)`（`resolve()` 后必须仍在 workspace 内，否则 400）；导出目录固定 `assets/export/`；补路径穿越测试（`..`、绝对路径、符号链接）。

### S2. `content_path` 越权读写
- 证据：写 `/text` 用 `canvas.root() / node.data["content_path"]`（`server/app.py:2235-2239`）；读 `core/canvas.py:670-698 read_text`；`GET /api/canvas` 的 `content` 字段回显（`server/app.py:2262`）。
- 影响：通过 `POST /nodes/{id}` 改 `content_path` 即可写任意文件，也可读任意文件（信息泄露）。
- 修法：`content_path` 只允许 `assets/<node_id>/…` 规范形态；读写都走 `safe_workspace_path`；legacy 数据做一次性迁移或兼容白名单。

### S3. `POST /nodes/{id}` 的 `data` 是任意浅 merge
- 证据：`server/app.py:2186`（`data: dict | None`，`update_node` 浅合并）。
- 影响：可伪造 `takes`、`rendered_by`、`content_path`，甚至改 `active_generation_id` 让正在跑的任务“被过期”，绕过状态机与版本历史。
- 修法：按节点类型白名单（可改：`prompt`/`label`/`note`/`position`；只读：`takes`/`rendered_by`/`active_generation_id`/`content_path`）；状态只能由 Worker 或专用接口改。

### S4. 无认证、无 CORS 策略、无限流
- 证据：`server/app.py` 无 auth 中间件；`/api/agent` 可让 Agent 使用工具与文件系统。
- 影响：当前假设“本机单用户”；一旦部署到局域网/公网即完全开放。
- 修法：token 中间件（`API_TOKEN` env，空则仅 127.0.0.1 绑定）、CORS 白名单、`/api/agent` 与写接口限流；部署文档写清“默认只监听本机”。

## 二、契约与一致性

### C1. 12 个写接口的 `revision` 仍可省略（第 8 项）
- 端点：`connect`、`edges/delete`、`arrange`、`nodes/{id}/position`、`nodes/{id}`（更新）、`nodes`（创建）、`upload-media`、`canvases/{name}/rename`、`canvas/approvals`、`canvas/run`、`canvas/composition-approvals`、`canvas/compose`。
- 现状：`_require_revision` 对 `None` 放行；只有 `/text`、`/take`、`DELETE canvas`、`DELETE node` 用了严格版 `_require_write_revision`。
- 影响：外部脚本/程序化调用可以绕过版本校验；并发下“最后写入者赢”仍可能在非前端路径发生。
- 修法（已与用户确认“全严格，无后门”）：`revision` 必填→缺 400 `code=canvas_revision_required`；过期→409 `canvas_revision_conflict`；**拒绝必须在 consume 审批之前**；同步改 `web/canvas.js`、`demo/*.py`（约 15 处）、补 12 端点×3 情况参数化测试。

### C2. 画布是整块 JSON + 单 revision，并发粒度太粗
- 影响：拖动位置与生成写回共用同一写单元，高频拖动放大 409；`_mutate_canvas_with_retry` 只能缓解不能消除。
- 长期：位置写走独立轻量通道（或 per-node version / CRDT），生成写回只改自身节点。

### C3. 删除画布/节点不清理产物文件
- 影响：`assets/` 只增不减；删除后 take、生成视频仍占磁盘，且无法从 UI 恢复。
- 修法：引用计数或 GC 任务（按 canvas 节点引用 + take 引用），删除时标记待回收，定时清理。

### C4. 审批 TTL 固定 600 秒
- 证据：`core/invocation_store.py:115`（`expires_at = now + 600`）。
- 影响：用户看完审批去开会，回来重试即 409“审批已失效”。
- 修法：TTL 按任务类型可配（env），过期后返回明确“重新审批”而不是普通 409。

### C5. 导出接口不校验 revision
- 证据：`server/app.py:2427`（`ExportCanvasRequest` 无 revision；只读 + 落盘）。
- 若导出算“写入”（生成 md 文件），应与 S1 一起纳入严格 revision 或改为纯内存返回。

## 三、异步任务层（P0-4 范围 + 生产化）

### A1. 无取消、无超时、无事件流
- 现状：只有 `queued/running/unknown/succeeded/failed/discarded`；`/api/media/jobs/{id}` 轮询；无 `POST /cancel`。
- 修法：见架构方案第 9 项（状态机加 `cancelled/timed_out`、`deadline_at`、取消语义、SSE 事件总线 + 轮询兜底）。

### A2. Worker 单实例串行
- 证据：`core/media_job_store.py:466-493`（`MediaJobWorker._run` 一次一个 job）。
- 影响：一个 30 分钟视频阻塞同进程全部画布。
- 修法：并发池（按 provider 限流）+ 每 provider 队列。

### A3. 默认全内存，重启即丢任务
- 证据：`server/app.py:64` `create_media_job_store()` 默认 memory；`/api/health` 的 store 字段可见。
- 影响：进程重启后任务丢失、节点永久 `generating`，用户只能手工重跑。
- 修法：生产环境强制 `MEDIA_JOB_STORE_BACKEND=redis|postgres`；启动自检不达标拒绝启动；补“哪些 env 必须一起切”的部署契约（job store + invocation + event + canvas 四者一致）。

### A4. 租约过期只在 claim 时发现，无后台 sweep
- 影响：没有新任务进来时，“僵尸 running”一直挂着。
- 修法：定时 sweep（把过期 running 标 unknown/requeue）。

### A5. 无重试策略、无限流、无成本预算
- 影响：Provider 瞬时 5xx 直接 failed；重复审批可重复扣费（当前只靠同一审批的 `job_key` 幂等）；无单次/单日成本上限。
- 修法：可重试错误指数退避（幂等前提）；预算上限（每次运行/每日累计，超限拒绝）；限流按 provider。

### A6. 任务回写与 production stage 双写，无事务
- 影响：任务 failed 但阶段停在 generating；跨对象状态不一致。
- 修法：阶段推进以任务终态为唯一事实源（事件驱动），或引入 outbox（当前 `outbox_publisher` 为 null）。

### A7. 无优雅停机 drain
- 影响：重启会中断 running 任务；虽然 `CancelledError` 走 `mark_unknown`，但体验是“结果不确定”。
- 修法：停机时停止 claim、等待 lease 内任务完成或标记 requeue；K8s 用 preStop。

## 四、业务能力（按产品需求排，不是 bug）

### B1. 首尾帧接力不可用
- 证据：Provider 支持 `first_frame`/`last_frame`（`core/media.py:344`、`:372`），但画布 `build_media_request` 不传；`video_ref` 端口会把 mp4 当图片 data URL 发出去（`core/media.py:_media_url`）。
- 影响：“上一镜尾帧接下一镜首帧”的短剧核心玩法在画布链路不可用。
- 修法：请求构造补 first/last frame；`video_ref` 语义改为“取末帧图片”（ffmpeg 抽帧）或“视频续写参数”。

### B2. 视频生成不消费音频入边；无音频生成 Provider
- 现状：`generation_jobs` 只取 IMAGE/VIDEO 引用；音频只在时间线合成时用；TTS 只在合成时调用。
- 修法：明确产品语义（口播驱动视频？）后再加；新增 audio Provider 接口。

### B3. 角色一致性不足
- 现状：靠参考图 + 文字描述；`consistency_tags` 只进 `asset_desc`，不进 Provider 请求；无 seed；`subjects[].id` 不贯通；重名不校验。
- 修法：请求带 seed（可复现）、角色卡结构化（id/多角度参考图/固定描述文本）、生成时注入；重名报错。

### B4. 无 ComfyUI 适配器
- 现状：只有 Mock 与 HTTP 第三方 API（`MediaProvider Protocol` 仅 `list_models/generate/resume`）。
- 修法：新增 ComfyUI Provider（工作流 JSON 模板 + 参数映射 + 轮询/WS 进度），已有接口可承载。

### B5. 参数能力窄且静默
- 时长 clamp 到 1–30 秒（`generation_params`）无用户提示；画幅只支持 480/720/1080p（`_QUALITY_HEIGHTS`）；模型能力（时长/分辨率）未与 Provider 元数据校验。

### B6. 分镜总时长与片段时长无对账
- 体检只校验单镜 3–8 秒；合成前无“总时长 = 各段之和”校验，成片可能超/欠时长。

## 五、数据与运维

### D1. 存储粒度与查询效率
- `canvases.content` 整块 JSONB（`migrations/0001_durable_state.sql`）；`list_canvases` 全量 load；`get_canvas` 逐节点读正文文件（N+1）。
- 修法：列表只查 meta 摘要列；正文内容懒加载；项目多了再考虑拆表。

### D2. 无数据库迁移框架
- 只有 `0001` 种子；Postgres 后端靠 env 选；没有升级/回滚流程，也没有“file→postgres 一致性”校验工具。

### D3. 资产元数据无外键/回收
- `media_assets` 与画布节点引用之间无约束；删除不联动；资产库 UI 尚未覆盖全部资产类型。

### D4. 旧数据分叉只做读兼容
- `outputs.prompt/text` 与 `data.prompt` 并存的历史画布，只做了读侧兼容；没有一次性迁移脚本（写侧已在新代码统一）。

### D5. 可观测性薄
- 只有 P0-14 的 `logger.exception`；无请求 ID、结构化日志、指标（任务量/耗时/失败率/费用）、审计（谁在何时消耗了审批）。

### D6. 无备份/恢复流程
- 画布是单 JSON 文件 + `content.md` 目录；删了无法恢复；无定时备份、无导入导出（整库）。
