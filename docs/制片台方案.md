# 制片台改造方案（Studio）

> 一句话：**把「Agent 编排画布」降级为内部结构视图，在上面长一个「制作者用的」三段式制片台——剧本 / 资产 / 制作 / 预览。**
> 保留现有 Agent、Skill、校验、媒体管线、成片管线；不推倒重来。
>
> **2026-10 修订（见第 11 节）**：画布不再写进「明确不做」。画布的问题不是"该不该有"，而是**角色错了**——它现在只是 Agent 编排结果的可视化，下一步要变成**制作者手里的节点即工具视图**（每个节点 = 一个确定性工具契约 + 一串可点的「尝试」）。视觉层 v2 已落地。

- 版本：2026-10-17（第 11 节修订 2026-10）
- 约束：面试复试 2026-10-20（周二）下午；可用工时 ≈ 25–30h
- 演示目标：**60 秒内跑完一条真闭环**（新建 → 剧本 → 分集 → 资产 → 片段 → 生成 → 挑版 → 导出）

---

## 0. 为什么改（一句话证据）

| 证据 | 结论 |
|---|---|
| 两个独立实现（开源 huobao-drama、某商业产品）工作台都是「左栏流水线 + 中间列表 + 右栏检查器」，**都没有节点画布** | 画布不适合承载人的生产管理，只适合展示 Agent 编排 |
| 一集 12 片段 × 60 集 ≈ 700+ 片段 | 人管理 700 条数据的唯一方式是**表格 + 筛选 + 状态列** |
| 现有 9 张画布 89 节点：asset 40 个、**0 个有图**；video_gen 7 个、**0 个有产出**；全 workspace **0 个 mp4/srt/wav** | 系统在「生成之前」武装到牙齿，在「生成之后」手无寸铁 |
| 后端 11,219 行 vs 前端 3,859 行 | 注意力错配：引擎很重，人手很轻 |
| LibTV 编辑态画布（实测）：每个节点卡底下挂「尝试」动作列表，如文本节点「**自己编写内容** / 文本视频 / 图片反推提示词 / 文字生音乐」，脚本生成器「脚本生成分镜脚本 / 角色生成分镜脚本 / **自己编写分镜脚本**」 | 「人来做」是节点的**第一等选项**，不是兜底；节点 = 工具，不是 Agent 的产物 |

## 1. 目标信息架构

```
项目（Project）
├── 剧本（分集列表）        ← 阶段一：粘贴/上传剧本 → 自动分集 → AI 改编
├── 资产                  ← 阶段二：角色(×形象) / 场景 / 道具 / 音色
├── 制作（片段队列）        ← 阶段三：片段列表 → 提示词 → 生成 → 挑版
└── 预览 / 导出            ← 阶段四：集级拼接 → 播放 → 下载 → 标记完成
```

顶栏常驻：`项目名 · 第N集 · 画面比例 9:16 · 模型 xxx · 画质 480P · 完成度 2/12`

左侧栏常驻流水线（5 步，状态由**数据推导**，不靠人点）：
`剧本 → 原始内容 → AI 改编 → 资产 → 片段生成 → 导出`

## 2. 数据模型：旁挂，不动 `core/canvas.py` 的结构

**原则**：所有新信息挂在 `canvas.meta.*` 与节点 `data.*` 上；老画布无这些字段时按「无数据」降级，不报错。

### 2.1 `canvas.meta`

```jsonc
{
  "project": {
    "region": "国内", "genre": "都市情感",
    "style_preset": "写实电影",          // 对应 asset(kind=style) 节点
    "aspect_ratio": "9:16",
    "video_model": "seedance-2.0-mini",
    "quality": "480P"
  },
  "episodes": [
    { "no": 1, "title": "梦中的东京", "script_node_id": "n_xxx",
      "chars": 1187, "status": "in_progress" }
  ],
  "production": { "export_done": false }
}
```

### 2.2 `asset.data`（角色多形象是本次核心差异化）

```jsonc
{
  "kind": "character",           // 已有：character | scene | prop | style
  "name": "宫水三叶",
  "role": "protagonist",         // 新增：protagonist | supporting | extra（主角/配角/龙套）
  "voice_id": "v_xxx",           // 新增：音色绑定（可继承角色级）
  "description": "…",            // 已有
  "consistency_tags": ["…"],     // 已有
  "looks": [                     // ★ 新增：一个角色的 N 套形象
    { "id": "look_1", "name": "系守高中校服",
      "image_path": "assets/generated/xx.png",
      "prompt": "三视图：正脸特写 + 正面/90°侧面/背面…",
      "locked": true,
      "appearances": [{ "ep": 1, "scenes": ["1-2"] }] }
  ],
  "active_look_id": "look_1"
}
```

**兼容策略**：老资产无 `looks` → 用 `outputs.ref.value.path`（若有图）或 `data.image_path` 合成一个隐式 `look_default`。前端一律按 `looks` 渲染。

### 2.3 `storyboard.data`（沿用现有 `shots`，补台词可机读）

现有每个 shot 的 6 字段是 `subject / action / shot_size / camera_move / sound / duration`——
**台词目前被塞在 `sound` 字段里**（如 `"sound": "陈小满：一共两块五。阿岸：姐，扫码。"`）。这是可用的隐式编码，不重构，改为**显式化**：

```jsonc
{ "no": 4, "segment_no": 1, "subject": "陈小满与阿岸", "action": "…",
  "shot_size": "中景", "camera_move": "固定",
  "sound": "扫码枪嗒、纸带落台",       // ← 只留环境音
  "dialogue": [                        // ★ 新增：可机读台词
    { "speaker": "陈小满", "line": "一共两块五。", "kind": "dialogue" },
    { "speaker": "阿岸",   "line": "姐，扫码。",   "kind": "dialogue" }
  ],
  "duration": 4.0 }
```

迁移：读取时若 `dialogue` 缺失，跑一次 `parse_dialogue(sound)`（正则 `^([^：:]{1,10})[：:]\s*(.+)$`）兜底。写入时两者同步（`sound` 只留非台词部分）。

### 2.4 `prompt.data`（片段 = 一个视频生成任务）

```jsonc
{
  "segment_no": 1, "episode_no": 1,
  "duration_s": 17,                  // 新增数值型（现有是字符串 "17s"）
  "references": [                    // ★ 新增：有序引用，取代隐式 {{ref N}}
    { "asset_id": "n_82886d", "look_id": "look_1", "ordinal": 1 },
    { "asset_id": "n_4cc983", "look_id": null,     "ordinal": 2 }
  ],
  "ref_limit": 12,
  "content_path": "assets/n_707ac9/content.md"
}
```

`outputs.prompt.value` / `outputs.text.value` 仍是**纯文本提示词**（人可读可改），其中引用写成 `@角色名` / `@场景名`；
生成前由后端按 `references` 的 `ordinal` 替换为模型可识别的参考图标记。**引用按名字/ID，不按序号排列位置。**

### 2.5 `video_gen.data`（版本用任务表承载）

```jsonc
{ "segment_no": 1, "current_take_id": "media_xxx:n_88ffbe", "tags": ["人脸漂移"] }
```

- **take 历史不新建表**：直接查 `media_job`（`core/media_job_store.py` 已有 `MediaJob`），
  `payload.node_id == 本节点 id && status == "succeeded"` 的记录即历史，按时间倒序。
- 节点 `outputs.video.value.path` = 当前选中版（等价于 huobao 的 `storyboards.video_url` 指针）。
- 好处：零新表；坏处：查询要扫 payload → 加一个 `iter_jobs_by_node(node_id)` 辅助函数 + 内存索引。

## 8. 面试要讲的五件事

1. **业务本质**：在不确定性里批量出货。12 片段 × 5 抽 × 60 集 = 3600 次调用，制作者管的是**废片率**与**返工成本**。
2. **三个杠杆**：资产锁定降方差 → 结构化提示词降方差 → take 管理与评级消化剩余方差。（呼应「服务于业务=服务于钱」）
3. **产品架构**：项目 → 集 → 片段 → 资产×形象 → take。
4. **两个独立实现都不约而同不用画布** → 所以我把画布降级为结构视图。
5. **边界与下一步**：双模型审核界限不一致 / 关键帧与转场帧 / Skill 版本化 / 超时 fallback / 成本看板。

**明确不做**（每条配一句为什么）：多集真实生成、团队资产库、音色与 BGM、敏感词过滤、成本看板。
（原「画布重做」一項 **2026-10 撤回**，理由与后续做法见第 11 节。）

## 9. 从 huobao-drama 借的 6 条（已在 `tmp/ref/huobao-drama`）

1. 分镜时长算术：`总时长 = 字数÷500字/分`、`段数 ≈ 总时长÷12s ±20%`、`段时长 ≥ 台词字数÷4.5字/秒 + 2s`
2. 两级粒度：片段 8–15s 含 2–4 子镜，子镜 2–6s，段内不跨场景
3. 视频提示词：信息头 + **每 3 秒一行**，段数 = `ceil(duration/3)`；`@名字` 由代码映射参考图
4. 三种图种分开：角色=三视图、场景=无人物空镜、道具=白底单品；风格词由代码注入
5. 道具「判定三问 + 一集 0–3 个，宁可少提」
6. 成本护栏：默认只跑未生成 / 选择模式才许重出 / 批量前二次确认列清单 / 失败单独重试

## 11. 画布交互模型 v2：节点即工具契约（2026-10 修订）

### 11.1 为什么撤回「不做画布重做」

前面第 8 节的判断没错——**画布不适合承载 700 条片段的生产管理**，制片台仍然是主入口。
错的是把结论推到"画布这个媒介不行"。真正的病灶是**画布上只有 Agent 的编排结果，没有制作者的落手处**：

- 卡片里的内容全是 AI 产的，人改不了；改一次就要回去跟 Agent 说话，等于把"编辑"退化成"聊天"。
- 60 秒短剧不是一次生成，是**在不确定性里批量出货**。制作者真正要的是：这一张卡换模型/换提示词/换参考图重跑一次，以及"两版并排挑一版"。
- 所以画布的正确角色是 **结构视图 + 单卡干预**：制片台管"这一集到哪一步了"，画布管"这一卡怎么再抽一次"。

### 11.2 三档随时降级（不是二选一）

| 档位 | 谁在编排 | 画布的角色 | 现状 |
|---|---|---|---|
| L0 全自动 | Agent 铺完整草稿 | 只读回看 | 已有（`runCanvas` 整图执行） |
| L1 人搭骨架 + AI 执行单卡 | 人连边、人点「尝试」 | 主要工作面 | **待建（本节重点）** |
| L2 人全手动 | 人上传/自己写 | 素材台 + 时间线 | 部分（上传/替换入口已有） |

关键：**任何时刻能往下降一档，且降档不丢 Agent 已经产出的东西**。现在的问题就是只有 L0。

### 11.3 五个机制（可排期）

1. **尝试预设（attempt presets）** —— 每张卡按类型给一串具名动作，第一个永远是"人来做"。
   - 文本/提示词卡：`自己编写内容` / `文本生成视频` / `图片反推提示词` / `生成分镜脚本`
   - 图片卡：`自己上传` / `图片高清` / `图生图`
   - 视频卡：`自己上传` / `重新抽一版` / `首尾帧生成` / `延长 5s`
   - 资产卡：`自己上传` / `AI 生成三视图` / `锁定为参考`
   - 落点：`web-vue/src/components/ToonNode.vue`（卡片上的 `尝试` 区）+ `CanvasPanel.vue` 的 `cardItems`
2. **单卡重跑 / 选区执行** —— 现在只有整图 `runCanvas`。要能：选中一张卡 → 只跑这张；框选一片 → 只跑这片。
   - 后端已有单节点执行语义，缺的是前端入口与"只跑选中"的入参。
   - **P1 已落地单卡**：点开任意一张生成卡 → 工作台的「生成」= `runCanvas({ approved: true, only: [这张卡] })`（「选区执行」仍未做，要等框选工具）。
3. **候选组（candidate group）** —— 同一张卡的 N 次产出并排成一组，标"可用/废片"，选中的那版才往下游供料。
   - 对应第 6 节 take 管理，落到节点上就是 `data.takes[]` + `data.selectedTake`。
   - **P1 已落地数据与切版**：每次生成追加一版 `data.takes[]` 并写 `current_take_id`，历史抽屉可逐版对比、一键切回；"并排成一组摆到画布上"与"可用/废片"标注仍未做。
4. **锁定 / 冻结（lock）** —— 人认可的卡上一把锁：Agent 再编排、整图再跑都不许改它的内容与位置。
   - 这是 L1 档敢让 Agent 继续跑的前提；没有锁，人做的每一步都会被下一次 Agent 冲掉。
5. **来源可见（data.source）** —— 每张卡标清 `Agent 生成 / 人上传 / 人编写 / 复用（来自哪张卡）`，视觉上要能一眼看出"这张是我改过的"。
   - 没有这个标记，人不敢在 Agent 的作品上动手。

### 11.5 版本历史（P1 第 1 项，已落地 2026-10）

以前的问题：`/api/canvas/run` 只把结果写进 `node.outputs[port]`，**重新生成等于覆盖上一版**——制作者既不能对比，也不能回退。现在：

- 服务端 `server/app.py::_execute_media_job` 写回结果时，同时把这一版追加进 `node.data["takes"]`（末尾追加、只留最近 30 版），并把 `node.data["current_take_id"]` 指到新版。take 结构与制片台既有字段一致：`{take_id, path, mime, provider, mock, model, duration_s, shot_no, mode, created_at, rating, note}`，画布这条路径的 `mode = "canvas"`。
- 新增 `POST /api/canvas/nodes/{node_id}/take`（body `{canvas, take_id}`）：把某一版设为当前版，同步改写 `outputs[port]` —— 与制片台的 `POST /api/studio/segments/{id}/take` 改的是**同一份 takes**，所以两边看到的版本一致。
- 画布侧 `web-vue/src/store.js` 的 `selectTake` 改走画布接口；`NodeStudio.vue` 生成完成后 `loadCanvas()`，历史按钮上的版本数实时更新；`GenerationHistoryDrawer.vue` 的 `modeLabel` 补 `canvas → 画布生成`，切版后**不再自动关抽屉**（还要接着比对下一版）。
- 实测链路：单卡连跑两次 → `takes` 0→1→2、`current_take_id` 每次指向新版 → 打开历史（2 版、带「当前」徽标）→ 点另一版「设为当前版」→ 抽屉不关、`outputs` 与预览图随之切换。截图：`docs/canvas-v2/16-p1-takes-history.png`、`17-p1-take-switched.png`。
- 仍未做：画布上"两个候选并排"的摆法（现在只在抽屉里纵向列出）、`rating/note` 的人工标注入口、锁定与来源标记。

### 11.6 单卡对话（P1 第 2 项，已落地 2026-10）

工作台最下面多了一个输入框：**说的话只对这张卡生效**。这是把「改一点东西要跟主 Agent 来回好几轮」这件事按代价拆开——一张图的措辞、一句话的时长，不该牵动整张画布。

- 请求带 `focus_node`（`server/app.py` 的 `ChatRequest.focus_node`）：服务端读到它就把工具收窄到 `NODE_SCOPE_TOOLS = {get_canvas, update_node, set_text, export_prompt, word_count}`，新建、删除、连线、改故事板这些本轮**根本不发给模型**；同时把这张卡的 id／标题／类型／状态／当前正文／已有 data 字段／上游依赖拼进 `<node-scope>` 系统提示，并约束「改完只说改了什么」。
- 每个节点一条**独立会话**：`web-vue/src/store.js` 的 `askNode()` 首次对话时 `POST /api/sessions` 建一条标题为「节点工作台：<节点名>」的会话，id 记在 localStorage（`toonflow-node-session`）。这样单卡来回不会掺进画布会话那条几万 token 的长历史，也不会挤它的上下文压缩。
- 前端：`NodeStudio.vue` 底部新增 `.studio-chat`（我／Agent 气泡、回车发送、Shift+回车换行、运行中显示「改着呢…」）；`tool_execution_end` 带画布变更时自动 `loadCanvas()`，卡片当场跟着变。
- 实测：让它在 `n_image_gen`（分镜07·桌游店首帧）上说「把标题改成…」→ 它调 `update_node` 改了这一张，回复「标题已改：…，其它字段和状态保持不变」，画布节点数 52／连线 10 不变；再让它「新建一个 video 节点并连线」→ 它答「本轮工具只能操作当前这张卡（n_image_gen），没有新建节点和连线的能力，所以这步得回整图画布做」，一次工具都没调。主画布会话（`c38ff298`，54 条消息）没有被写入，隔离有效。截图：`docs/canvas-v2/18-p1-node-chat.png`、`19-p1-node-chat-reply.png`。
- 仍未做：单卡对话里直接触发「重跑这一张」（现在要用户点工作台的「生成」按钮，属于有意为之——生成必须是人明确点的）；节点会话在侧边栏会单独出现，暂不合并。
